# [Backstage](https://backstage.io) on AKS

A Backstage app with Microsoft Entra ID sign-in, packaged as a container image and a Helm chart for AKS. The chart exposes Backstage through the Gateway API using the AKS application routing implementation (`approuting-istio`) and terminates TLS with the managed default domain certificate.

| Path | What it is |
| --- | --- |
| `Dockerfile` | Multi-stage build. Installs, type-checks, and bundles the backend (which also serves the frontend) inside Docker. Runs as the non-root `node` user (uid 1000). |
| `charts/backstage` | Helm chart: Backstage, optional in-cluster PostgreSQL, Gateway, HTTPRoutes, and `DefaultDomainCertificate`. |
| `.github/workflows/publish.yaml` | Lints, builds and pushes the image to GHCR, and publishes the chart to GHCR as an OCI artifact. |
| `azure-setup/` | OpenTofu for the AKS Automatic cluster with application routing, Gateway API, and the default domain. |
| `entra-setup/` | OpenTofu for the Entra app registration and the `backstage-users` group. |
| `hack/kubeconform-schemas/` | JSON schemas for the Gateway API and `DefaultDomainCertificate` CRDs, generated from the cluster, used by kubeconform. |

## Run locally

```sh
yarn install
yarn start
```

Local Entra settings live in `app-config.local.yaml`, which is generated by `entra-setup/` and gitignored. Never commit it.

## Build the image

The build needs nothing on the host besides Docker (or Podman). No `yarn install` or `yarn build` step is required first.

```sh
docker build -t backstage:local .
```

### Smoke test against PostgreSQL

```sh
docker network create backstage
docker run -d --name backstage-pg --network backstage \
  -e POSTGRES_USER=backstage -e POSTGRES_PASSWORD=backstage \
  postgres:17.11-trixie

docker run --rm --name backstage --network backstage -p 7007:7007 \
  -e POSTGRES_HOST=backstage-pg -e POSTGRES_PORT=5432 \
  -e POSTGRES_USER=backstage -e POSTGRES_PASSWORD=backstage \
  backstage:local
```

Then check `curl http://localhost:7007/.backstage/health/v1/readiness` and open http://localhost:7007. Clean up with `docker rm -f backstage-pg && docker network rm backstage`.

## Deploy to AKS

### Prerequisites

1. The cluster from `azure-setup/` (AKS Automatic with `approuting-istio`, the managed Gateway API CRDs, and the default domain enabled).
2. The Entra app registration from `entra-setup/`, applied after `azure-setup/` because it reads the default domain from that state. Its redirect URI is `https://backstage.<default-domain>/api/auth/microsoft/handler/frame`, so use `backstage` as the hostname label below.
3. `kubectl` connected to the cluster, Helm 3.8 or later (OCI support), and OpenTofu (`tofu`) to read the setup outputs.

```sh
az aks get-credentials \
  --resource-group "$(tofu -chdir=azure-setup output -raw rg_name)" \
  --name "$(tofu -chdir=azure-setup output -raw aks_name)"

export NAMESPACE=backstage
export BACKSTAGE_HOST="backstage.$(tofu -chdir=azure-setup output -raw default_domain)"
```

The default domain certificate is a single-level wildcard (`*.<id>.<region>.aksapp.io`), so the hostname must be exactly one label under the default domain.

### Create the secret

The chart never takes secret values directly. `appConfig` references environment variables with `${ENV_VAR}` placeholders, and the chart loads them from the Secret named in `existingSecret`. The default `appConfig` expects these keys:

| Key | Value |
| --- | --- |
| `AZURE_CLIENT_ID` | Application (client) ID of the `backstage` app registration |
| `AZURE_CLIENT_SECRET` | Client secret of the app registration |
| `AZURE_TENANT_ID` | Directory (tenant) ID |
| `AZURE_GROUP_ID` | Object ID of the `backstage-users` group |
| `GITHUB_TOKEN` | Optional. GitHub token for the GitHub integration |

`entra-setup/` outputs every value except `GITHUB_TOKEN`, so create the Secret straight from its state without copying anything by hand:

```sh
tofu -chdir=entra-setup output
```

```text
client_id = "00000000-0000-0000-0000-000000000000"
client_secret = <sensitive>
group_id = "00000000-0000-0000-0000-000000000000"
tenant_id = "00000000-0000-0000-0000-000000000000"
```

```sh
kubectl create namespace "$NAMESPACE"

kubectl -n "$NAMESPACE" create secret generic backstage-secrets \
  --from-literal=AZURE_CLIENT_ID="$(tofu -chdir=entra-setup output -raw client_id)" \
  --from-literal=AZURE_CLIENT_SECRET="$(tofu -chdir=entra-setup output -raw client_secret)" \
  --from-literal=AZURE_TENANT_ID="$(tofu -chdir=entra-setup output -raw tenant_id)" \
  --from-literal=AZURE_GROUP_ID="$(tofu -chdir=entra-setup output -raw group_id)"
```

`output -raw` prints the sensitive `client_secret` value, so pass it straight to `kubectl` as above instead of echoing it. To add the optional GitHub token, append `--from-literal=GITHUB_TOKEN="$(gh auth token)"` or a token of your choice.

The client secret rotates with `time_rotating` in `entra-setup/`. After a rotation and `tofu apply`, recreate the Secret and restart Backstage so it picks up the new value:

```sh
kubectl -n "$NAMESPACE" delete secret backstage-secrets
# rerun the create command above, then:
kubectl -n "$NAMESPACE" rollout restart deployment/backstage
```

### Publish the image and chart

Publish both artifacts to GHCR by hand from this repo. The image goes to `ghcr.io/<owner>/backstage-demo` and the chart goes to `oci://ghcr.io/<owner>/charts/backstage-demo`, the same locations CI uses, so you can switch to [CI publishing](#publish-from-ci) later without changing the install command.

You need a personal access token (classic) with the `write:packages` scope. Commit your changes first: the image tag comes from the commit SHA, so an uncommitted build would publish code that doesn't match its tag.

```sh
export GHCR_USER=<github-username>
export GHCR_TOKEN=<token-with-write:packages>
export GHCR_OWNER="$(echo "$GHCR_USER" | tr '[:upper:]' '[:lower:]')"

git diff --quiet HEAD || echo "Uncommitted changes. Commit before publishing."
export IMAGE_TAG="sha-$(git rev-parse --short=7 HEAD)"
export CHART_VERSION="0.1.0-${IMAGE_TAG}"
```

Build and push the image. The AKS nodes are amd64, so build for `linux/amd64` even on an Apple silicon Mac; the build runs under emulation and is slow. The `source` label links the package to this repository on GitHub. With Podman, swap `docker` for `podman`.

```sh
echo "$GHCR_TOKEN" | docker login ghcr.io -u "$GHCR_USER" --password-stdin

docker build --platform linux/amd64 \
  --label org.opencontainers.image.source=https://github.com/pauldotyu/backstage-demo \
  -t "ghcr.io/${GHCR_OWNER}/backstage-demo:${IMAGE_TAG}" .
docker push "ghcr.io/${GHCR_OWNER}/backstage-demo:${IMAGE_TAG}"
```

Package and push the chart. `--app-version` pins the chart to the image you just pushed, so installs don't need `image.tag`.

```sh
echo "$GHCR_TOKEN" | helm registry login ghcr.io -u "$GHCR_USER" --password-stdin

helm package charts/backstage --version "$CHART_VERSION" --app-version "$IMAGE_TAG" -d /tmp
helm push "/tmp/backstage-demo-${CHART_VERSION}.tgz" "oci://ghcr.io/${GHCR_OWNER}/charts"
```

Check what was published:

```sh
helm show chart "oci://ghcr.io/${GHCR_OWNER}/charts/backstage-demo" --version "$CHART_VERSION" | grep -E '^(version|appVersion)'
```

`CHART_VERSION` is a prerelease (`0.1.0-sha-<short-sha>`), so each commit gets its own chart version. Pushing the same commit again overwrites both artifacts.

#### Package access

New GHCR packages owned by a personal account are private. Choose one:

- **Public (simplest for a demo):** on GitHub, open your profile, then **Packages**. For both `backstage-demo` and `charts/backstage-demo`, open **Package settings** and select **Change visibility** > **Public**.
- **Private:** the cluster needs a pull secret for the image. The token you published with works, because `write:packages` includes `read:packages`; a separate `read:packages` token is safer to leave in the cluster. Helm is already logged in from publishing, so it can pull the chart.

  ```sh
  kubectl -n "$NAMESPACE" create secret docker-registry ghcr-pull \
    --docker-server=ghcr.io \
    --docker-username="$GHCR_USER" \
    --docker-password="$GHCR_TOKEN"
  ```

  Then add `--set 'imagePullSecrets[0].name=ghcr-pull'` to the `helm upgrade --install` command below.

### Publish from CI

`.github/workflows/publish.yaml` publishes the same artifacts, but only for pushes to `main` and `v*.*.*` tags. Pull requests run the lint and image build without pushing anything. See [CI/CD](#cicd) for what each trigger produces.

```sh
gh pr create --base main --fill
gh pr checks --watch
gh pr merge --squash
gh run watch     # follow the publish run on main
```

If you published by hand first, the workflow's `GITHUB_TOKEN` may not have write access to those packages. If the push fails with `403`, open each package's **Package settings**, then under **Manage Actions access** add this repository with the **Write** role.

### Install the chart

From GHCR, after publishing:

```sh
helm upgrade --install backstage oci://ghcr.io/pauldotyu/charts/backstage-demo \
  --version "$CHART_VERSION" \
  --namespace "$NAMESPACE" \
  --set gateway.hostname="$BACKSTAGE_HOST" \
  --set existingSecret=backstage-secrets
```

Prerelease versions (manual `0.1.0-sha-<short-sha>` and CI `0.1.0-main.<run>`) are only installed when you pass `--version` or `--devel`. Each chart version's `appVersion` is the image tag built from the same commit, so you don't need to set `image.tag`.

The chart lives in `charts/backstage` but is named `backstage-demo` in `Chart.yaml`, so it publishes as `charts/backstage-demo` and doesn't collide with other `backstage` charts under the same GHCR owner. Helm takes the published name from `Chart.yaml`, not the directory. Resource names still come from the release name: release `backstage` creates `backstage`, `backstage-postgresql`, and so on.

From this repo, pinning an image you built:

```sh
helm upgrade --install backstage charts/backstage \
  --namespace "$NAMESPACE" \
  --set gateway.hostname="$BACKSTAGE_HOST" \
  --set existingSecret=backstage-secrets \
  --set image.tag=sha-<short-sha>
```

### Test a local build before pushing

To try image or chart changes on the cluster before CI publishes anything, push a locally built image to [ttl.sh](https://ttl.sh), an anonymous registry where images expire, and install the chart from this repo. Complete the prerequisites and create the Secret first.

The AKS nodes are amd64, so build for `linux/amd64` even on an Apple silicon Mac. The build runs under emulation and is noticeably slower than a native build. With Podman, swap `docker` for `podman`.

```sh
# ttl.sh images are public. A random name keeps the image from being guessed or overwritten.
export IMAGE_NAME="backstage-demo-$(uuidgen | tr '[:upper:]' '[:lower:]' | cut -c1-8)"
# The tag sets how long the image lives (max 24h). Pick one that outlasts your testing,
# or pods can't pull the image after a reschedule.
export IMAGE_TAG=4h

docker build --platform linux/amd64 -t "ttl.sh/${IMAGE_NAME}:${IMAGE_TAG}" .
docker push "ttl.sh/${IMAGE_NAME}:${IMAGE_TAG}"

helm upgrade --install backstage charts/backstage \
  --namespace "$NAMESPACE" \
  --set image.registry=ttl.sh \
  --set image.repository="$IMAGE_NAME" \
  --set image.tag="$IMAGE_TAG" \
  --set gateway.hostname="$BACKSTAGE_HOST" \
  --set existingSecret=backstage-secrets
```

To redeploy after a change, push to a new tag. With `pullPolicy: IfNotPresent`, nodes keep using a cached image for a reused tag.

```sh
export IMAGE_TAG=4h-2
docker build --platform linux/amd64 -t "ttl.sh/${IMAGE_NAME}:${IMAGE_TAG}" .
docker push "ttl.sh/${IMAGE_NAME}:${IMAGE_TAG}"
helm upgrade backstage charts/backstage -n "$NAMESPACE" --reuse-values --set image.tag="$IMAGE_TAG"
```

### Verify

```sh
kubectl -n "$NAMESPACE" wait --for=condition=Available defaultdomaincertificate/backstage --timeout=5m
kubectl -n "$NAMESPACE" wait --for=condition=Programmed gateway/backstage --timeout=5m
kubectl -n "$NAMESPACE" rollout status deploy/backstage
curl -sS -o /dev/null -w "HTTP %{http_code} verify=%{ssl_verify_result}\n" "https://$BACKSTAGE_HOST/"
curl -sI "http://$BACKSTAGE_HOST/" | head -1   # 301 to https
```

DNS records are published by the managed `external-dns` and can take a minute. Once the checks pass, open `https://$BACKSTAGE_HOST` and sign in with Entra. A `verify=0` result means the certificate is trusted.

### Troubleshoot

```sh
# Image pull errors and deployment safeguard rejections
kubectl -n "$NAMESPACE" describe pod -l app.kubernetes.io/component=backstage
kubectl -n "$NAMESPACE" logs deploy/backstage
kubectl -n "$NAMESPACE" describe defaultdomaincertificate backstage
kubectl -n "$NAMESPACE" describe gateway backstage
# Hostname does not resolve
kubectl logs -n app-routing-system deployment/default-domain-dns-external-dns
```

### Uninstall

```sh
helm uninstall backstage -n "$NAMESPACE"
kubectl -n "$NAMESPACE" delete pvc -l app.kubernetes.io/component=postgresql
kubectl delete namespace "$NAMESPACE"
```

The in-cluster PostgreSQL PVC is not removed by `helm uninstall`. Delete it before reinstalling, or the newly generated password will not match the existing data.

## Chart reference

### Configuration layering

Backstage loads config in this order, and later files win:

1. `app-config.yaml` (baked into the image)
2. `app-config.production.yaml` (baked into the image)
3. `app-config.helm.yaml`, rendered from the chart into a ConfigMap

The chart sets `app.baseUrl`, `backend.baseUrl`, and `backend.cors.origin` to `https://<gateway.hostname>` (or `baseUrl` if set), then merges `appConfig` on top. Changing `appConfig` rolls the pods. Set a key to `null` in your values to drop a chart default, for example `appConfig.catalog.providers.microsoftGraphOrg: null`.

```yaml
appConfig:
  organization:
    name: Contoso
  integrations:
    github:
      - host: github.com
        token: ${GITHUB_TOKEN}
```

### Gateway and TLS

With `gateway.enabled: true` (default) the chart creates, in the release namespace:

- `DefaultDomainCertificate` that asks AKS to write the managed wildcard certificate into the Secret `<release>-tls`. The Gateway must be in the same namespace as that Secret.
- `Gateway` with `gatewayClassName: approuting-istio`, an HTTPS listener on 443 that terminates TLS with that Secret, and an HTTP listener on 80.
- `HTTPRoute` attached to the HTTPS listener that routes to the Backstage Service.
- `HTTPRoute` attached to the HTTP listener that returns a 301 redirect to HTTPS (`gateway.httpsRedirect`).

To use your own certificate, set `gateway.tls.defaultDomainCertificate: false` and `gateway.tls.secretName` to a TLS Secret in the release namespace.

### Database

| Mode | Values |
| --- | --- |
| In-cluster PostgreSQL (default, demos only) | `postgresql.enabled: true`. Single replica StatefulSet with an 8Gi PVC. The password is generated into `<release>-postgresql` and preserved across upgrades, or set `postgresql.auth.existingSecret`. |
| External database (real use) | `postgresql.enabled: false`, `externalDatabase.host`, `externalDatabase.user`, and a password key (`POSTGRES_PASSWORD` by default) in `externalDatabase.existingSecret` or `existingSecret`. `PGSSLMODE` defaults to `require`. |

Example for Azure Database for PostgreSQL flexible server:

```yaml
postgresql:
  enabled: false
externalDatabase:
  host: <server-name>.postgres.database.azure.com
  user: backstage
  existingSecret: backstage-secrets   # contains POSTGRES_PASSWORD
```

Backstage creates one database per plugin, so the user needs `CREATEDB`. If it cannot have that, set `appConfig.backend.database.pluginDivisionMode: schema`.

### AKS Automatic safeguards

AKS Automatic enforces deployment safeguards and the Pod Security baseline. The chart sets resource requests and limits, startup, liveness, and readiness probes, topology spread constraints, distinct Service selectors, non-root users, read-only root filesystems, and dropped capabilities for both Backstage and PostgreSQL. Image tags are always explicit; `latest` is never used.

## CI/CD

`.github/workflows/publish.yaml` runs on pull requests, pushes to `main`, and `v*.*.*` tags.

| Job | Pull request | `main` | Tag `v1.2.3` |
| --- | --- | --- | --- |
| Lint (actionlint, `helm lint --strict`, kubeconform `-strict`) | Yes | Yes | Yes |
| Build image (`linux/amd64`) | Build only | Push `sha-<short>`, `main` | Push `sha-<short>`, `1.2.3` |
| Publish chart to `oci://ghcr.io/<owner>/charts` | No | `0.1.0-main.<run>` | `1.2.3` |

The chart job sets `appVersion` to `sha-<short-sha>`, the image tag built from the same commit, so a chart version always deploys the image built alongside it. Pushes use the workflow `GITHUB_TOKEN` with `packages: write`, and image provenance is attested with `actions/attest-build-provenance`.

## Validate locally

```sh
for v in charts/backstage/ci/*.yaml; do
  helm lint charts/backstage --strict -f "$v"
  helm template backstage charts/backstage -f "$v" \
    | kubeconform -strict -summary -kubernetes-version 1.36.0 \
        -schema-location default \
        -schema-location 'hack/kubeconform-schemas/{{.Group}}/{{.ResourceKind}}_{{.ResourceAPIVersion}}.json'
done
actionlint
```

To regenerate the CRD schemas after a Gateway API or application routing upgrade, export the CRDs from the cluster and convert them with kubeconform's `openapi2jsonschema.py` (requires PyYAML):

```sh
curl -fsSL -o /tmp/openapi2jsonschema.py https://raw.githubusercontent.com/yannh/kubeconform/master/scripts/openapi2jsonschema.py
for crd in gateways.gateway.networking.k8s.io httproutes.gateway.networking.k8s.io defaultdomaincertificates.approuting.kubernetes.azure.com; do
  group=$(kubectl get crd "$crd" -o jsonpath='{.spec.group}')
  kubectl get crd "$crd" -o yaml > "/tmp/$crd.yaml"
  (cd "hack/kubeconform-schemas/$group" && FILENAME_FORMAT='{kind}_{version}' python3 /tmp/openapi2jsonschema.py "/tmp/$crd.yaml")
done
```
